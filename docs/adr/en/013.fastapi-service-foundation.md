# ADR-013: FastAPI service foundation: layout, dependencies, startup, unified errors, database access, current user, login/logout, knowledge-base access checks, vector search, rerank and refusal, agent endpoint

## Status
Accepted

## Context
The plan is to rewrite KnowFlow's core backend path in Python (FastAPI), one module at a time: session auth and tenant isolation → ingestion → retrieval → streaming Q&A → eval. The rewrite is matched against the existing TypeScript implementation by **HTTP behaviour**: the same request must get the same status code and response shape, so one set of HTTP tests can run against both versions.

The first phase only lays the foundation and is not wired to the frontend. A few hard-to-reverse things had to be settled first: where the code lives, which packages it depends on, how it runs alongside Next.js, and how errors are returned. Relevant constraints:

- `CLAUDE.md`: every change must be runnable without additional setup; new dependencies need confirmation first; API response shapes don't change.
- Existing endpoints all return `{ requestId, ok, data?, error? }` (`lib/api/response.ts`). The new service must keep this shape.
- Business endpoints need to know who is calling: keep ADR-006's opaque database sessions. The browser sends the `rag_session` cookie and the server looks the user up in the `sessions` table. The new service connects to the same Postgres and reads the same tables.
- A knowledge base belongs to a workspace, and any member of that workspace can access it. A non-member gets the same 404 as for a missing knowledge base, so ids can't be probed (ADR-007). The retrieval, file and conversation endpoints rewritten later all have to pass this check first.

FastAPI's default error shapes all differ from KnowFlow's (measured on fastapi 0.150.0, 2026-10-20):

| Case | FastAPI default |
| --- | --- |
| Unknown route | 404 `{"detail":"Not Found"}` |
| Raising `HTTPException` | Its own status code, `{"detail":"…"}` |
| Field validation failure | **422** `{"detail":[…]}`; each error carries `"input"`, the raw value the user submitted |
| Body is not valid JSON | **422** `{"detail":[…]}` |
| Body missing entirely | **422** `{"detail":[…]}`; the error `type` is `"missing"`, the same as for a missing field, and `loc` is only `("body",)` (measured 2026-10-21) |
| Uncaught exception | 500, plain text `Internal Server Error` |

## Decision

### Layout and dependencies
- The service lives in `services/api/`; its dependencies are pinned in `services/api/requirements.txt`:
  - `fastapi==0.150.0`: defines routes and validates requests; bundles Starlette (request/response, middleware, exception handling, TestClient) and Pydantic (validation from type annotations)
  - `anyio==4.15.1`: Starlette already depends on it, so no extra package is installed. Rerank uses it for the overall deadline, for cancelling requests, and for hopping from the thread pool back to the event loop, so it is declared directly
  - `uvicorn==0.54.0`: the server process that listens on the port and sends and receives HTTP
  - `pytest==9.1.1`: the test runner
  - `httpx2==2.15.1`: the HTTP client `TestClient` needs; `embeddings.py` also uses it to call OpenRouter, so no second HTTP dependency is added
  - `psycopg[binary]==3.3.6` (two lines in `requirements.txt`: `psycopg` and `psycopg-binary`): the Postgres driver, running handwritten SQL directly; it supports both sync and async styles, and the `binary` build ships compiled libraries, so nothing is compiled on install
- The virtual environment `services/api/.venv/` stays out of git (`services/api/.gitignore`).

### Startup
- In development, open two terminals at the repository root: Next.js runs as before with `pnpm dev` (port 3000); the Python service runs with `pnpm dev:api` (`127.0.0.1:8000`, auto-reload). Stop with `Ctrl+C`; if the port is taken, use `pnpm dev:api --port 8001`.
- One-time install: from the repository root, run `python3 -m venv services/api/.venv`, then `services/api/.venv/bin/python -m pip install -r services/api/requirements.txt`.
- `scripts/dev-api.mjs` reads the root `.env.local` with the existing `dotenv` dependency (already-exported variables take precedence), then starts uvicorn with the virtual environment's Python. `DATABASE_URL` and `OPENROUTER_*`, which retrieval needs, are passed to the Python child process; no manual `source` is needed. The script does not install dependencies or run migrations or seed scripts.
- Database tests still need an explicit `DATABASE_URL` pointing at a local test database; the startup script plays no part in pytest. Tests use a fake embedding and need no OpenRouter variables.
- In this phase Next.js does not call the Python service. Without Python installed, the existing app runs as before.

### Paths
- All endpoints live under `/api`, for example `/api/health`. When the frontend is wired up later, the paths map one-to-one to the existing endpoints, and the comparison tests use the same paths.
- Exception (2026-11-14): `POST /api/chat/agent` exists only in the Python version; the TS version has no counterpart. It is the non-streaming endpoint for the tool-calling loop: the model decides what to search for and how many times, and the server runs the searches. It sits under `/api/chat/` because it takes the same kind of input as TS's `/api/chat/stream` (a question plus an optional conversation), and its request fields reuse the names from there: `message`, `conversationId`, `knowledgeBaseId`. It is not under `/api/rag/`, where `/api/rag/search` takes a search query and returns chunks.

### Unified response shape and error mapping
- Success: the route calls `success(data)` and returns 200 `{ requestId, ok: true, data }`.
- Failure: `{ requestId, ok: false, error }`, where `error` is a string and extra information goes in `data`, matching `error(message, data?)` in `lib/api/response.ts`.

| Case | Status | `error` |
| --- | --- | --- |
| Unknown route | 404 | `"Not Found"` |
| Business error: raise `HTTPException` with an explicit status and a `detail` that is safe to show | That status | `detail` as is |
| Business error that needs extra data: raise `ApiError(status, message, data)` | `status` | `message`; `data` goes into the response's `data`, for example `{"code": "UNAUTHORIZED"}` when not logged in |
| Field validation failure | **400** | The failing field and the reason, for example `"name: Input should be a valid string"`; **without the submitted value**. When several fields fail at once, only the first error is returned |
| Body is not valid JSON, or missing entirely | **400** | `"invalid_request"`, matching `parseJsonBody` (`lib/api/route.ts`): with an empty body, `req.json()` also throws `SyntaxError` |
| Uncaught exception | 500 | `"internal_error"`, **with no exception details**; the full stack trace goes to the log together with the requestId |

The two kinds of error are handled separately:

- **Business errors** are things the user needs to know, for example that a file is still being parsed (KnowFlow returns 409) or a file is over the size limit (413). Raise `HTTPException` with an explicit status and a `detail` the user may see. When the response's `data` must carry information (an `HTTPException`'s `detail` is just a string and can't hold it), raise the custom `ApiError` instead; its handler calls `failure(request, status, message, data)`. `failure` only puts `data` into the response when it receives some, matching the TS `error(message, data?)`.
- **Unexpected errors** (code bugs, an unreachable database) always return 500 `"internal_error"`.

Implementation notes:
- The exception handler is registered on `starlette.exceptions.HTTPException`. It is the parent class of `fastapi.HTTPException`; registering only the latter leaves unknown routes returning `{"detail":"Not Found"}`.
- Handlers are also registered for `fastapi.exceptions.RequestValidationError` and `Exception`.
- The validation-error handler looks only at the first error. If its `type` is `"json_invalid"` (not valid JSON), or its `loc` is only `("body",)` (body missing entirely), it returns `"invalid_request"`. Otherwise it drops the leading `"body"` from `loc` and joins the rest with `.` as the field name. A missing body and a missing field both have `type` `"missing"`; only `loc` tells them apart.

### requestId
- Middleware generates it when the request arrives (`uuid4`) and stores it on `request.state`. It is written to the response body's `requestId` and the `X-Request-Id` response header, and logs carry it.
- The middleware is a plain ASGI class, `RequestIdMiddleware`, not `@app.middleware("http")`: the `receive` wrapped by the latter (`BaseHTTPMiddleware`) never sees a client disconnect, so `request.is_disconnected()` in a route stays `False` forever (measured on starlette 1.9.0, 2026-10-31).
- The 500 handler (registered on `Exception`) adds the response header itself. Starlette puts the `Exception` handler in the outermost `ServerErrorMiddleware`, outside our middleware; that response is sent outside it, never passes through the middleware's `send`, and the header step never runs. The 4xx handlers sit inside the middleware (`ExceptionMiddleware`), so their responses pass through it as usual and need nothing extra.
- A valid UUID sent by the frontend is used in preference; otherwise one is generated; a value that is not a UUID is never used. The basis: KnowFlow's chat endpoint (`app/api/chat/stream/route.ts:83-85`) prefers the requestId sent by the frontend, because the frontend uses the same UUID as the assistant message's id (`lib/hooks/use-chat-stream.ts:411-412`). The frontend puts it in the chat request's JSON body, not in a header, so the chat endpoint reads and validates it and then overrides the value the middleware generated. No endpoint in this phase receives a requestId from the frontend, so generating one is enough.

### Database access
- The database URL comes from the `DATABASE_URL` environment variable. It is not hard-coded, and the code does not parse `.env.local`.
- `get_db()` is a dependency with `yield`: each request opens one connection with `with psycopg.connect(...)`, hands it to the route, and closes it automatically when the request ends. No connection pool for now.
- SQL parameters always use `%s` placeholders and are passed separately; strings are never concatenated into SQL.
- `uuid` columns come back as Python `uuid.UUID`. They are converted to strings at the boundary so that, as in the TS version, ids are strings throughout the code. Otherwise `UUID(...) == "..."` silently returns `False` and permission checks go wrong.

### Current user
Behaviour matches the TS version item by item:

| | Python | TS counterpart |
| --- | --- | --- |
| cookie | Named `rag_session` | `lib/auth/cookie.ts` |
| Current user, `get_current_user` (dependency) | With no cookie, returns `None` without querying the database. Otherwise joins `sessions` and `users` on `sessions.id = token` and `expires_at > now()`, returning `{id, email}` if found and `None` if not | `getCurrentUser`, `getSessionUser` (`lib/auth/current-user.ts`, `lib/auth/sessions.ts`) |
| Login required, `require_user` (dependency) | With no current user, raises `ApiError(401, "Unauthorized", {"code": "UNAUTHORIZED"})` | `requireUser` |
| `GET /api/auth/me` | Always 200: `{user: {id, email}}` or `{user: null}`, so the frontend can probe the login state | `app/api/auth/me/route.ts` |

Business routes declare `user=Depends(require_user)` in their parameters: when the caller is not logged in, the route function never runs, so no endpoint has to repeat the check at the top.

### Login and logout

**Password verification** (`verify_password` in `services/api/auth.py`, counterpart of `verifyPassword` in `lib/auth/password.ts`):
- Keeps the stored format `scrypt$N$r$p$salt(base64)$hash(base64)`. The parameters are read from the string, the hash is recomputed with the standard library's `hashlib.scrypt`, and the comparison is constant-time with `hmac.compare_digest`. A malformed value returns `False` rather than raising.
- Every existing account's hash was produced by the TS version, so the Python version must accept them as they are: `test_password.py` tests with a hash generated by TS `hashPassword`, which TS `verifyPassword` has also verified, and the local demo account (generated by `scripts/seed-demo.ts`) can log in to the Python version (measured with uvicorn and curl, 2026-10-24).

**Login `POST /api/auth/login`**:

| Request | Python | TS version |
| --- | --- | --- |
| Valid JSON with unacceptable content: not an object, a missing field, not a string, a password under 8 characters | 401 `"Invalid email or password"`, with `data` `{"code": "BAD_CREDENTIALS"}` | Same |
| Unknown email, wrong password | Identical to the row above | Same |
| Not valid JSON, or an empty body | 400 `"invalid_request"` | **500**, with the raw `SyntaxError` message as `error` (the login endpoint does not use `parseJsonBody`) |
| Body is `null` | 400 `"invalid_request"` (FastAPI treats `null` as no body) | 401 |
| Success | Creates a session (`secrets.token_urlsafe(32)`, expiring after 30 days), sets the cookie, 200 `{user: {id, email}}`; the email returned is the one stored in the database | Same |

- The body is received as `body: Any = Body()`, not as a Pydantic model: FastAPI only parses the JSON (on failure the validation-error handler returns 400), and the route checks the content itself, raising the same 401 for any item that fails.
- Email lookup is case-insensitive: `lower(email) = lower(%s)`, matching `getUserByEmail`.
- The email is only checked to be a string and trimmed, not checked for format: the format was validated at registration, a malformed email finds no user, and the result is the same 401, so the external behaviour matches the TS version.
- Cookie attributes match `lib/auth/cookie.ts` (`HttpOnly`, `SameSite=lax`, `Path=/`, `Max-Age` of 30 days). `Secure` is turned on by the environment variable `COOKIE_SECURE=1` and is off by default, because local development is over http.
- Login and logout call `conn.commit()` explicitly before the route returns, instead of relying on the commit when `get_db`'s `with` block finishes. Measurement showed that the client receives the response first and the teardown runs afterwards (with a 0.3-second wait in the teardown, the client had the response in under 0.01 seconds). Otherwise a client that sends a request immediately with the new cookie might not find the session.
- Routes such as login and logout, which do synchronous database work and CPU work (one scrypt takes about 22 ms), are written as `def`: FastAPI runs them in the thread pool so they don't block other requests.

**Logout `POST /api/auth/logout`**: with a cookie, deletes the matching session (with no cookie, it doesn't query the database); clears the cookie (`Max-Age=0`); always returns 200 `{ok: true}`, matching `endSession`.

**Not handled yet:** for an unknown email the endpoint returns 401 immediately without verifying a password, while a known email with a wrong password runs scrypt first. The responses are identical, but their timing differs by almost 20 ms, which reveals whether an email is registered. The TS version behaves the same; this phase stays consistent with it, and whether to fix it is a separate decision.

### Knowledge-base access check

**Dependency `require_knowledge_base`** (counterpart of `requireKnowledgeBaseAccess` in `lib/authz/access.ts`, plus `parseUuidParam` in the `GET` route) checks, in order:

| Request | Python | TS version |
| --- | --- | --- |
| Not logged in | 401 `"Unauthorized"`, with `data` `{"code": "UNAUTHORIZED"}` (from `require_user`) | Same (`withAuth`) |
| id is not a UUID, for example `not-a-uuid` | 400 `"Invalid knowledge base id"`, without querying for the knowledge base | Same |
| id without hyphens, or with a `urn:uuid:` prefix | Treated as the same UUID | **400**: the regex in `lib/validation.ts` accepts only the hyphenated 8-4-4-4-12 form |
| The knowledge base doesn't exist | 404 `"Knowledge base not found"`, with no `data` | Same |
| The knowledge base exists, but the caller isn't a member of its workspace | Identical to the row above (apart from the requestId) | Same |
| A member, whatever the role | Returns the knowledge base | Same |

- "Exists" and "is a member" are decided by **a single SQL query**: `where id = %s and workspace_id in (select workspace_id from workspace_members where user_id = %s)`, the same `userWorkspaceIds` subquery as TS `getKnowledgeBaseById`. No code path can tell "doesn't exist" from "not a member", so the guarantee that the 404 leaks nothing comes from the structure, not from two branches happening to return the same thing.
- The id is parsed with `uuid.UUID` first, and a parse failure returns 400. **SQL receives the parsed value, not the raw string.** `uuid.UUID` is looser than Postgres: `urn:uuid:…` passes Python's parser, but the raw string handed to Postgres raises `InvalidTextRepresentation` and the endpoint returns 500 (measured 2026-10-26). The id is parsed once, and only the parsed value is used afterwards.
- The dependency returns the shaped knowledge base, like `requireKnowledgeBaseAccess`; a route gets it by declaring `kb=Depends(require_knowledge_base)`. The dependency reads the path parameter by name, so the path must be written `{knowledge_base_id}`: with `{id}`, FastAPI treats `knowledge_base_id` as a required query parameter and returns 400 `"knowledge_base_id: Field required"` (measured 2026-10-26).

**`GET /api/knowledge-bases/{knowledge_base_id}`** (counterpart of `GET` in `app/api/knowledge-bases/[id]/route.ts`) returns 200 `{knowledgeBase}`, in the same shape as `toKnowledgeBase` in `lib/db/knowledge-bases.ts`:
- camelCase keys: `id`, `name`, `description`, `createdAt`, `updatedAt`. A single knowledge base has no `chunkCount`; only the list endpoint includes it.
- Timestamps match JS `toISOString()`: converted to UTC, truncated to milliseconds, ending in `Z`. psycopg returns `timestamptz` in the database session's time zone (`Etc/UTC` in local Docker), so the value is converted with `astimezone(timezone.utc)` before formatting, and the result doesn't depend on the database's time-zone setting.
- When `description` is `NULL`, the key is left out: the TS version writes `?? undefined`, and `JSON.stringify` drops keys whose value is `undefined`. An empty string is returned as usual.

Listing, creating, updating and deleting knowledge bases are not rewritten in this phase; the TS version still owns them.

### Vector search

`POST /api/rag/search` (counterpart of `app/api/rag/search/route.ts`) does vector recall only by default, like the TS version; rerank and refusal are covered in the next section. A request goes through these steps in order:

1. `require_user`: 401 when not logged in.
2. `parse_search_request`: validates the body, with the same order and error messages as the TS version.
3. `require_knowledge_base_access`: 404 for a non-member or a missing knowledge base.
4. Call the embedding to turn the question into a vector. The question is passed as is, without trimming, like the TS version.
5. `vector_search_chunks`: searches only this knowledge base for cosine distance `< maxDistance`, ascending by distance, and takes the first `topK`.

- **Requests without access or with bad parameters cost no embedding.** That is why the access check is a plain function that the route calls after validation; the path-parameter dependency `require_knowledge_base` reuses it too. FastAPI dependencies run before the route body, so as a dependency the 404 would come back before the 400, in a different order from the TS version.
- **`get_embed_query` returns the function without calling it.** The route calls it after steps 2 and 3; tests replace it with a fake through `dependency_overrides`, without network access or cost.
- SQL uses named parameters such as `%(vector)s`: the same vector is used three times but passed only once. The vector is formatted as the text `[x,y,…]` and cast with `::vector` in SQL, because `<=>` can't decide which operator to use from two parameters of unknown type.
- `embeddings.py` (counterpart of `embedChunk` in `lib/rag/embeddings.ts`) reads `OPENROUTER_API_KEY`, `OPENROUTER_BASE_URL`, `OPENROUTER_EMBEDDING_MODEL` and `OPENROUTER_EMBEDDING_DIMENSIONS`, times out after 30 seconds, and checks that the result is a 1536-dimensional vector of finite numbers. A failed call goes through the unified 500, with the requestId in the log.

Differences from the TS version, all intentional:

| Request | Python | TS version |
| --- | --- | --- |
| `mode` is `keyword` or `hybrid` | 400 `"mode … is not supported yet"` | Searches normally |
| With `fileId` or `filter` | 400 `"… is not supported yet"`: silently ignoring `filter` would also return chunks the caller explicitly excluded | Searches normally |
| `topK` is fractional, for example `2.5` | 400 `"topK must be between 1 and 20"` | **500**: calls the embedding first, then Postgres reports `invalid input syntax for type bigint` (measured 2026-10-30) |

`topK: 5.0` is still accepted: JSON `5.0` is a float in Python, but in JS it is simply the integer 5. The range check must come before `int(top_k)`; otherwise the infinity that `1e400` parses to makes `int()` raise. `topK: null` returns 400: the default applies only when the field is absent, like a JS destructuring default, so the code uses `body.get("topK", default)` and not `or` (`or` would replace `0` and `null` with the default and return 200).

**Side-by-side check** (2026-10-30, local database, `topK: 20`): 3 questions on Olympus Demo and 2 on topk-cost-check were sent to both versions. The returned chunk objects were exactly the same, including their order and `_distance`. topk-cost-check's results contained 10 groups of chunks with equal distances, and their order matched this time too, but neither side's SQL has a secondary sort key, so this is not guaranteed.

### Rerank and refusal

TS's `/api/rag/search` has no rerank and no refusal; they exist only in the chat and eval paths (`lib/rag/retrieve.ts`, `lib/rag/refusal-gate.ts`). So this adds an optional parameter, `rerank: true`; without it, the response is exactly as before. Steps 2 and 3 are unchanged, and after them the steps become:

4. Call the embedding.
5. Recall: always 20 (`RETRIEVAL.recallTopK`), still filtered by `maxDistance`. `topK` does not affect the recall width; otherwise rerank wouldn't see enough candidates.
6. Empty recall: return `refusal: "empty"` without calling rerank.
7. Rerank: the question is trimmed, the documents are the `embedding_text`, and `top_n` is 8. Chunks that got no result go last, in recall order, like the TS version.
8. Take the first `topK`, 5 by default.

The response `data` is `{chunks, refusal, rerank}`. `rerank.status` has only three values:

| Status | `reason` | Meaning |
| --- | --- | --- |
| `applied` | none | Rerank took effect; chunks carry `meta._rerankScore` |
| `skipped` | `disabled`, `single_candidate`, `no_candidates` | Rerank was not called |
| `fallback` | `timeout`, `network`, `upstream_error`, `invalid_response` | The call failed; falls back to recall order and still returns 200 |

- **Why this field exists:** a missing `_rerankScore` can mean that rerank failed, or that it was turned off, or that there was only one candidate. Relying on the score alone, the TS version can't tell these apart.
- **15-second overall deadline**, covering connecting, sending and reading the whole response body, implemented with `anyio.fail_after`. httpx's own timeouts count per read or write and never fire when upstream sends data a little at a time, so they are turned off.
- **Client disconnect:** while waiting for rerank, the route checks every 0.1 seconds. On disconnect it cancels the upstream request and returns 499 `"request_cancelled"`; this does not count as a service failure and does not fall back to recall order. It covers only the rerank step: the embedding is a synchronous call, and after a disconnect the route still waits for it to finish.
- **No low-score refusal:** the reranker scored an unanswerable near-miss 0.9055, higher than an answerable question's 0.8808, so a high score doesn't mean a question can be answered; the TS version's `minRerankScore` has always been 0 too (ADR-011).
- **The conversation-recap exemption is not ported:** `isConversationSummaryQuery` belongs to the chat path, and this endpoint has no conversation history.
- The route is a synchronous function running in the thread pool, while `is_disconnected` has to be called on the event loop, so `get_rerank` uses `anyio.from_thread.run` to run the async rerank back on the event loop. A missing `OPENROUTER_API_KEY` is a configuration error and returns 500; it does not count as `fallback`.

**Side-by-side check** (2026-11-01, local database, real embedding and rerank services): the TS side called `recallChunks` + `selectFinalChunks` directly, and the Python side sent `rerank: true` through a real uvicorn. For 4 questions, the top 5 chunks came back in the same order with the same rerank scores, all with status `applied`. For 1 out-of-scope question, both sides recalled nothing, and Python returned `refusal: "empty"` without calling rerank. One question's results contained chunks with equal scores whose order also matched this time, but that is not guaranteed. `fallback` and client disconnect were not triggered against the real services; only tests cover them.

### Agent endpoint

`POST /api/chat/agent` (only the Python version has it; see "Paths") lets the model decide what to search for and how many times. The server runs the searches and returns the complete answer in one response, not as a stream. The code is in three places: `chat.py` calls the model, `agent.py` is the tool-calling loop (it touches neither HTTP nor the database; the caller passes in the model and the search), and `main.py` holds the route. The rules were settled one at a time in the study repository on 2026-11-13 and 11-14, tried against the real model, and then moved here.

Request body: `message` (required, non-empty string), `knowledgeBaseId` (required, UUID string), `conversationId` (optional, UUID). A request goes through these steps in order:

1. `require_user`: 401 when not logged in.
2. `parse_agent_request`: validates the body and returns 400 on errors. The field names and error messages follow TS's `/api/chat/stream`. The differences: `knowledgeBaseId` is required (the knowledge base is not looked up from the conversation), and `conversationId` may be left out (in which case there is no history).
3. `require_knowledge_base_access`: 404 for a non-member or a missing knowledge base.
4. When `conversationId` is given: `require_conversation_access` checks the conversation, returning 404 `"Conversation not found"` both when it doesn't exist and when it isn't yours. A conversation belonging to another knowledge base returns 400 (its history must not be combined with this knowledge base's material). Then `list_recent_messages` reads the latest 8 messages, oldest first, like the TS version.
5. `agent.run_agent`: gives the model the rules, the history and this question, and enters the loop.

When steps 1–4 fail, neither the model nor the embedding is called.

The response `data` is `{answer, citations, refusal, completed, stopReason, steps}`:

| Field | Meaning |
| --- | --- |
| `answer` | The answer; the fixed refusal sentence on a refusal; an empty string when the run didn't finish |
| `citations` | `[{number, chunk}]`: the chunks the answer cites, in the order their numbers first appear; `chunk` has the same shape as the chunks returned by `/api/rag/search` |
| `refusal` | `null`; `"empty"`: every search found nothing, and the program refused; `"model"`: chunks were found, and the model wrote the refusal sentence |
| `completed` | Whether the run finished |
| `stopReason` | `answered`, `no_search`, `max_model_calls`, `timeout`, `tool_failed`, `model_failed` |
| `steps` | One record per model call and per tool call, matching the log one to one, for example `{"type": "model_call", "toolChoice": "required", "result": "tool_calls"}` and `{"type": "tool_call", "id": "call_1", "query": "…", "found": 5}` |

An unfinished run still returns 200: a failed model call or search is not a fault in the request itself, so the caller reads `completed` and `stopReason`.

The rules of the loop:

- **Model**: `deepseek/deepseek-chat-v3.1`, `temperature: 0` (`chat.py`). All three `tool_choice` values, `required`, `auto` and `none`, were measured to work on this model. `openrouter/free`, the default in the TS model catalog, has not been verified for tool calling.
- **A single tool**, `search_knowledge_base`, whose only parameter is `query`. The route binds which knowledge base to search in a closure, and anything else the model writes into the arguments (for example another knowledge base's id) is ignored. Every search goes through the same steps as `rerank: true`: recall 20, distance `< 0.6`, rerank, take the first 5. The tool has no `mode` parameter: the Python version doesn't have keyword or hybrid search yet.
- **Search first**: until a search has run, `tool_choice` is `required`; after that it is `auto`. If the model doesn't comply and answers without searching, the loop stops with `stopReason` `no_search`, and the answer is not returned.
- **No search on the last call**: the model is called at most 4 times, and the 4th call's `tool_choice` is `none`, so the model can only answer or refuse from the chunks it already has. If no search has succeeded at all, the 4th call is still `required`. If the model doesn't comply and still asks for a tool on the 4th call, the call is not executed, and `stopReason` is `max_model_calls`.
- **Which errors go back to the model and which stop the loop**: the test is "could the model fix this error by rewriting the call once?" A badly written call (a tool name not in the list, arguments that aren't valid JSON, a missing `query`) can be fixed: it is not executed, and the error message is returned to the model as the result of that call (the real model corrected all three kinds). A failed search or a failed model call can't be fixed by the model: the loop stops with `stopReason` `tool_failed` or `model_failed` (`timeout` when the model call times out), and the real cause goes only to the log.
- **Refusal**: when every search is empty, the program returns the fixed refusal sentence directly (`refusal: "empty"`), regardless of what the model wrote. When chunks were found but don't contain the answer, the program can't tell, so it relies on the model writing the refusal sentence: an answer that starts with the refusal sentence counts as a refusal (`refusal: "model"`), and anything written after it is not returned, only logged. The refusal sentences are the same as in `lib/llm/refusal.ts`: Chinese when the question contains Chinese characters, English otherwise.
- **Citation numbers**: chunks from several searches are numbered consecutively, and a chunk seen again keeps its first number; otherwise both searches would have a `[1]`, and a `[1]` in the answer couldn't be traced back to its source. Out-of-range and repeated numbers are dropped. The rules follow `buildQaPrompt`, with one addition: ignore bracket numbers in earlier messages of the history.
- **30-second overall deadline**: each model call receives the time remaining, and `chat.py` uses `anyio.fail_after` to interrupt a request in progress, rather than only checking between calls.
- **History is read-only**: the history is read from the database, and this turn's question and answer are not written back to the conversation. So the history only contains messages saved by the TS chat UI.
- Tests: `test_agent.py` tests the loop's rules with a fake model that replies from a script, without the database; `test_agent_route.py` tests the endpoint layer with a fake model, real database searches, and rerank replaced by one that keeps recall order.

**Real run** (2026-11-15, local Olympus Demo knowledge base, real model, embedding and rerank, through the route itself): "奥林匹斯计划的首席研究员是谁？" ("Who is the lead researcher of the Olympus project?") was answered correctly in 5.5 seconds with 3 citations; "奥林匹斯计划成员的工资是多少？" ("What are the Olympus project members paid?") was refused by the model (`model`); "怎么做红烧肉？" ("How do you make braised pork?") was refused by the program (`empty`).

**Finding: questions that don't name the project find nothing** (2026-11-14, same knowledge base). The short search queries the model writes almost never get under the 0.6 recall threshold: "首席研究员" ("lead researcher") has a nearest distance of 0.708, "首席研究员是谁？" ("Who is the lead researcher?") 0.707, and "奥林匹斯计划的首席研究员是谁" ("Who is the lead researcher of the Olympus project") 0.474. The fixed pipeline also recalls nothing for such questions and refuses (consistent with the 2026-09-29 investigation), and the agent spends 3 extra searches and 4 model calls on top (about 10 seconds). For the follow-up "她负责什么？" ("What is she responsible for?") with history, the model fills in the person's name itself and the search finds results. Temporary experiments (no code changed): asking in the tool description for queries written as complete questions didn't help; additionally putting the knowledge base's name into the rules let "首席研究员是谁？" find results, while the English question still found nothing. Only 4 single-turn questions were tried, so the model is not told the knowledge base's name for now; that waits for a formal comparison eval of the fixed pipeline against the agent.

### Test data
- Tests insert their own test user and session and delete the user at the end (the session goes with it through the foreign key's `ON DELETE CASCADE`), without relying on existing data in the database. Expired sessions are built with `expires_at = now() - interval`.
- Tests write to the database, so they fail immediately when `DATABASE_URL`'s host is not `localhost` or `127.0.0.1`, to avoid writing to a remote database by mistake; when `DATABASE_URL` isn't exported, the database tests are skipped.
- The login tests' user has as its `password_hash` the TS-generated hash from `test_password.py`, which also verifies that Python accepts passwords stored by TS.
- The functions that create data live in `testdata.py` (users, sessions, workspaces, members, knowledge bases), and the `conn` fixture that connects to the database lives in `conftest.py`; all test files share them. Deleting a user also deletes, through foreign keys, that user's sessions and owned workspaces (together with their memberships and knowledge bases).
- The access-check tests set up two unrelated tenants (each with one workspace and one knowledge base), plus an ordinary member invited into one of the workspaces, covering "your own", "someone else's" and "a member of the same workspace". The "doesn't exist" and "not yours" responses must be exactly the same once the requestId is removed.

## Alternatives

### Detect rerank failure only by whether `_rerankScore` is present
Pros:
- The response shape is unchanged, with chunks exactly like the TS version's

Cons:
- Can't tell rerank failure from rerank being off or there being only one candidate

### Use httpx's `timeout=15`
Pros:
- No extra code

Cons:
- It times each connection, read and write separately, not the whole request; when upstream sends data a little at a time, the request can drag on forever

### Keep `@app.middleware("http")` and find another way to detect disconnects
Pros:
- The middleware doesn't change

Cons:
- It doesn't pass disconnects on to the route. Getting the original `receive` needs another wrapping layer outside it, which would then compete for the same channel with its internal message reading

### Make the access check a dependency of the search endpoint
Pros:
- Same style as `require_knowledge_base`, and a shorter route

Cons:
- Dependencies run before the route body; with field validation in the route, the 404 would come back before the 400, in a different order from the TS version (measured 2026-10-29)

### Compute the question vector inside a dependency
Pros:
- One less call in the route

Cons:
- The embedding would be called before validation and the access check, so requests without access would cost money too

### Silently ignore the not-yet-supported `mode`, `fileId` and `filter`
Pros:
- No extra checks to write, and these requests still return results

Cons:
- The scope the caller asked for is quietly widened, returning chunks that should have been excluded, and nothing shows it

### Check that `topK` is an integer with `isinstance(top_k, int)`
Pros:
- The simplest code

Cons:
- It rejects `5.0`, which the TS version accepts

### Put the service in a separate repository
Pros:
- Fully isolated from the product code, with no effect on the existing lint, build and CI

Cons:
- Both versions have to share the same Postgres and the same handwritten migrations (`db/migrations/`, ADR-004) and run the same comparison tests; in separate repositories, both the migrations and the API contract would have to be kept in sync across repositories

### Use `httpx` as the test client
Pros:
- Plenty of material: many tutorials and older docs use it in their examples

Cons:
- The current Starlette (1.9.0) imports `httpx2` first; with only `httpx` installed, every test run prints a deprecation warning (measured 2026-10-20)

### Start both services with one command (npm `concurrently`, docker compose, or a combined Makefile target)
Pros:
- A better development experience, with only one terminal open

Cons:
- `concurrently` is a new npm dependency; docker compose means maintaining another set of container configuration
- In this phase Next.js doesn't call the Python service, so there is no need to start them together. Decide when the frontend is wired up

### Keep FastAPI's default 422 and `{"detail": …}` shape
Pros:
- No code to write; clients get the full error for every field

Cons:
- Inconsistent with KnowFlow's 400 and unified shape: it breaks the "don't change API response shapes" constraint, and the comparison tests couldn't pass
- The default errors echo the submitted value back (`input`), so the login endpoint would return the password to the client

### Return the exception message on 500, as KnowFlow does
Pros:
- The caller sees the cause of the error directly

Cons:
- `routeErrorResponse` in `lib/api/route.ts` returns `e.message` as is, leaking internal details such as database errors and table names to the client
- Information the user needs should be returned as a business error, with a 4xx and an explicit `detail`, not passed through a 500

### Generate the requestId when building the response (copying `lib/telemetry/requestId.ts`)
Pros:
- Exactly like the TS version, and the simplest implementation

Cons:
- The requestId isn't available while the request is being handled, so logs can't carry it. The `console.error` at `lib/api/route.ts:20` has no requestId: when a user reports an error with the requestId from the response, the matching log can't be found

### Access the database through an ORM (for example SQLAlchemy)
Pros:
- Typed models and a query builder instead of handwritten SQL

Cons:
- The table structure would have to be defined again in Python, while its single source is the handwritten `db/migrations/` (ADR-004); the two easily drift apart
- The existing queries are few and simple, and plain SQL is easier to compare line by line with the TS version

### Use asyncpg
Pros:
- Good performance, natively async

Cons:
- Async only: every dependency and route touching the database would have to be `async def`. psycopg supports both sync and async, so the sync style can come first, and FastAPI runs sync routes in the thread pool

### Read `.env.local` in code with python-dotenv
Pros:
- No need to export environment variables in the terminal every time

Cons:
- One more dependency, and the code becomes tied to the path of a particular config file. With environment variables, the code doesn't care where the configuration comes from

### Use `HTTPException` for 401 too
Pros:
- No new exception class

Cons:
- `detail` is only a string and can't hold `data.code`; KnowFlow's 401 carries `{"code": "UNAUTHORIZED"}` (`lib/auth/current-user.ts`)

### Reuse the existing demo user in tests
Pros:
- No data to insert in tests

Cons:
- Depends on data that may change or be deleted at any time (for example by re-running `pnpm seed:demo`); only tests that create and delete their own data stay independent and repeatable

### Validate the login body with a Pydantic model
Pros:
- Fields and types are declared in the model, with less validation code

Cons:
- Unacceptable content would be turned into a 400 by the validation-error handler, while KnowFlow's login returns 401 `BAD_CREDENTIALS` for any unacceptable input (so nobody can use it to tell input errors from account errors); the comparison tests wouldn't match

### Check the email format with Pydantic's `EmailStr`
Pros:
- A stricter format check, close to zod's `.email()`

Cons:
- Needs the extra `email-validator` dependency, and it is redundant for login: a malformed email finds no user anyway, and the result is the same 401

### Base `Secure` on `NODE_ENV`, like the TS version
Pros:
- Both services share one switch

Cons:
- `NODE_ENV` is a Node convention whose meaning is unclear for a standalone Python process; `COOKIE_SECURE` says what it means

### Write the login route as `async def`
Pros:
- It could `await request.json()` and read the body itself

Cons:
- psycopg's synchronous calls and the scrypt computation would block the event loop, and every other request would have to wait meanwhile. As `def`, FastAPI runs it in the thread pool, and `Body()` parses the body without `await`

### Switch to a third-party password library such as bcrypt or argon2
Pros:
- More common algorithms and mature wrappers

Cons:
- Every existing hash in the database is in scrypt format; switching algorithms means making every user reset their password or migrating hashes at login. The standard library's `hashlib.scrypt` already verifies the existing hashes, with no new dependency

### Return 403 to non-members
Pros:
- More precise semantics: the knowledge base exists, the caller just lacks permission

Cons:
- Unlike 404, a 403 tells the caller that a knowledge base with this id exists, so ids can be probed; KnowFlow's convention is 404 for cross-tenant access (ADR-007)

### Check that the knowledge base exists first, then whether the caller is a member
Pros:
- Each step's meaning is more intuitive

Cons:
- One more query
- The code gains branches that can tell the two cases apart, so the 404 leaking nothing would depend on the two branches always returning exactly the same content, which later code changes could easily break

### Annotate with `uuid.UUID` and let FastAPI validate the path parameter
Pros:
- No parsing or `try` to write

Cons:
- The error text comes from Pydantic, for example `"knowledge_base_id: Input should be a valid UUID, invalid character: …"`, which differs from the TS version's `"Invalid knowledge base id"` (measured 2026-10-26)
- It also accepts the `urn:uuid:` prefix, so it is no stricter than `uuid.UUID`

### Check the id with the same regex as the TS version
Pros:
- Exactly like the TS version: ids without hyphens or with a `urn:uuid:` prefix also return 400

Cons:
- One more regex to maintain. These forms denote the same UUID, treating them as a UUID can't go wrong, and the frontend only sends the standard form, so this difference is accepted (see "Trade-offs")

### Let the agent answer without searching (`tool_choice: auto` from the start)
Pros:
- Small talk and similar questions save a search

Cons:
- The answer isn't grounded in the knowledge base, contrary to the convention of answering only from the knowledge base (ADR-011). Measured with `auto`, "你好" ("hello") got a direct answer without any search

### When every search is empty, let the model write the refusal sentence
Pros:
- The model can explain why nothing was found

Cons:
- The program already knows there is no material, so no judgement from the model is needed, and the model may answer from outside knowledge
- Detecting a refusal requires matching text, and the model's wording is unstable: the same question run three times was written three different ways (the refusal sentence plus an explanation, the refusal sentence alone, and an explanation first with the refusal sentence last)

### Still allow searching on the last call
Pros:
- One more chance to try a different query

Cons:
- Even if the last call's search finds something, there is no next call left to answer with. Measured: the "pay" question stopped at the call limit with an empty answer

### Pass the history in the request body
Pros:
- The endpoint doesn't depend on the conversation tables, and callers can assemble their own context

Cons:
- Callers could forge history, for example by inventing an assistant answer
- For the same `conversationId`, the TS chat endpoint and this one could see different histories

### Write this turn back to the conversation
Pros:
- The next turn could follow up on the agent's own answer

Cons:
- The written messages would appear in the TS chat UI, so the `retrieved_chunks` format and what the citation numbers mean would first have to be aligned with that side

## Trade-offs

Pros:
+ The same response shape and status codes as KnowFlow, so comparison tests can compare directly
+ Unexpected errors leak no internal information; errors the user should see go out as business errors and are still returned
+ Every log line can be found by requestId
+ No effect on the existing Next.js app, which runs without Python installed
+ Auth behaviour matches the TS version item by item: the same cookie, the same expiry check, the same `code` on 401, and `/me` always returning 200 in the same way
+ Existing accounts can log in to the Python version without migration: the scrypt hashes produced by the TS version are verified directly with the standard library
+ Cross-tenant access and a missing knowledge base return exactly the same 404, guaranteed by a single query
+ Search results are identical to the TS version field by field (5 questions compared side by side), and requests without access or with bad parameters cost no embedding
+ The agent can only search the one knowledge base the caller has access to: the knowledge base is bound on the server, and the model can only supply the search query

Cons:
- Development needs one more process running, and the Python service needs a one-time install
- Each request opens a new database connection, with no connection pool; once concurrency grows, a pool is needed
- The database tests need a local Postgres (Docker) running and an exported `DATABASE_URL`
- Field-validation error text comes from Pydantic and differs from the TS version's handwritten text; error messages the frontend shows directly have to be aligned one by one when each endpoint is rewritten
- Two intentional behaviour differences from KnowFlow: the error message on 500, and when the requestId is generated
- Two more inconsistencies between the login endpoint and KnowFlow: invalid JSON returns 400 (500 in TS), and a `null` body returns 400 (401 in TS)
- Response timing can still reveal whether an email is registered, as in the TS version; not handled for now
- The knowledge-base id check is looser than the TS version's: ids without hyphens or with a `urn:uuid:` prefix get 400 from TS but are treated as the same UUID here
- The search endpoint doesn't support `keyword`, `hybrid`, `fileId` or `filter` yet, so it can't replace the TS version
- A client disconnect can only cancel rerank, not the synchronous embedding call
- The order of chunks with equal distances isn't guaranteed, as in the TS version; not handled for now
- The agent endpoint isn't streaming, so a response can take up to 30 seconds; a client disconnect doesn't cancel the loop, and a rerank cancelled mid-search is recorded as `tool_failed`
- The agent has at most 4 model calls, with no margin: each badly written call uses one up, and a question with no answer uses up all 3 searches
- When a question doesn't name the project, recall comes back empty, and the agent refuses just like the fixed pipeline while spending several extra searches and model calls

## Consequences

- New endpoints all live under `/api` and return `success(data)` on success; errors the user should see raise `HTTPException` with an explicit status code and a `detail` that is safe to show.
- Tests live in `services/api/` and run with pytest and `TestClient`. Tests for 500s need `TestClient(app, raise_server_exceptions=False)`; otherwise the exception is raised inside the test.
- Code that queries the database gets a connection with `Depends(get_db)`; business routes that require login use `Depends(require_user)`; errors that need extra data raise `ApiError`.
- When to introduce a connection pool is decided once there is a concurrency need.
- Routes doing synchronous database work or heavy CPU work are written as `def`, not `async def`.
- The password-hash format is shared by the TS and Python versions; any change must be made on both sides at once.
- Deployments over https must set `COOKIE_SECURE=1`.
- When rewriting the chat endpoint: read `requestId` from the request body and, once it is validated as a UUID, use it to override the middleware's value, matching the behaviour of `app/api/chat/stream/route.ts:83-85`.
- Always run the access check before reading or writing a knowledge base's data. Routes that take the id from a path parameter declare `Depends(require_knowledge_base)` and write the path as `{knowledge_base_id}`.
- Endpoints that take the id in the request body (for example `POST /api/rag/search`) call `require_knowledge_base_access` directly in the route after validation.
- External calls that cost money always come after validation and the access check, and are provided through dependencies so tests can replace them.
- How the frontend connects to the Python service (for example Next.js forwarding by path prefix) will be decided in a separate ADR.
- Before the agent endpoint is wired to the frontend, decide whether to make it streaming, whether to write the agent's answers back to the conversation, and whether to tell the model the knowledge base's name (after a formal comparison eval).

## Notes

The rewrite turned up several problems in the TS version: `routeErrorResponse` returns `e.message` on 500, and its error log carries no requestId (`lib/api/route.ts:20-23`); the login endpoint returns 500 on invalid JSON, including the raw `SyntaxError` message (`app/api/auth/login/route.ts:10`, `:29-31`); response timing at login reveals whether an email is registered (`app/api/auth/login/route.ts:21-25`); a fractional `topK` on the search endpoint spends one embedding and then returns 500 (`app/api/rag/search/route.ts:45`); rerank's deadline is removed before the response body is read (`lib/rag/rerank.ts:74-76`); and a user cancellation and a service failure share the same `catch`, both falling back to recall order (`lib/rag/rerank.ts:70-72`). Whether to fix them in the TS version is a separate decision.
