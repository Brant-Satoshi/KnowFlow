# ADR-013：新建 FastAPI 服务的基础约定：目录、依赖、启动方式、统一错误格式、数据库连接与当前用户

## 状态
提议中（`feat/fastapi-foundation` 分支；合并前改为“已接受”，并补英文版和索引）

## 背景
计划逐模块用 Python（FastAPI）重写 KnowFlow 的核心后端链路：会话鉴权与租户隔离 → 上传入库 → 检索 → 流式问答 → eval。重写按**接口行为**对照现有 TypeScript 实现：同样的请求，状态码和响应格式要一致，同一套 HTTP 测试能分别跑两个版本。

第一阶段只搭基础，不接入前端。开工前要先定下几件难以回退的事：代码放在哪、依赖哪些包、怎么和 Next.js 一起运行、错误怎么返回。相关约束：

- `CLAUDE.md`：每个改动都要“不需要额外设置就能运行”；新增依赖要先确认；不改 API 响应格式。
- 现有接口统一返回 `{ requestId, ok, data?, error? }`（`lib/api/response.ts`）。新服务必须保持这个格式。
- 业务接口要知道“是谁在调用”：沿用 ADR-006 的不透明数据库 session，浏览器带 `rag_session` cookie，服务器到 `sessions` 表查用户。新服务要连同一个 Postgres，读同样的表。

FastAPI 的默认错误格式和 KnowFlow 都不一样（2026-10-20 在 fastapi 0.150.0 上实测）：

| 情况 | FastAPI 默认 |
| --- | --- |
| 不存在的路由 | 404 `{"detail":"Not Found"}` |
| 主动抛 `HTTPException` | 原状态码 `{"detail":"…"}` |
| 字段校验失败 | **422** `{"detail":[…]}`，每条错误带 `"input"`，即用户提交的原始值 |
| 请求体不是合法 JSON | **422** `{"detail":[…]}` |
| 请求体整个没传 | **422** `{"detail":[…]}`，错误的 `type` 和缺字段时一样是 `"missing"`，`loc` 只有 `("body",)`（2026-10-21 实测） |
| 未捕获的异常 | 500，纯文本 `Internal Server Error` |

## 决策

### 目录与依赖
- 服务放在 `services/api/`，依赖写在 `services/api/requirements.txt`，固定版本：
  - `fastapi==0.150.0`：定义路由、校验请求；自带 Starlette（请求/响应、中间件、异常处理、TestClient）和 Pydantic（按类型注解校验数据）
  - `uvicorn==0.54.0`：服务器进程，负责监听端口、收发 HTTP 请求
  - `pytest==9.1.1`：测试运行器
  - `httpx2==2.15.1`：`TestClient` 需要的 HTTP 客户端
  - `psycopg[binary]==3.3.6`（`requirements.txt` 里是 `psycopg` 和 `psycopg-binary` 两行）：Postgres 驱动，直接执行手写的 SQL；同时支持同步和异步写法；`binary` 版本带编译好的库，安装时不用本机编译
- 虚拟环境 `services/api/.venv/` 不进 git（`services/api/.gitignore`）。

### 启动方式
- 开发时开两个终端：Next.js 照旧 `pnpm dev`（3000 端口）；Python 服务在 `services/api/` 里运行 `.venv/bin/uvicorn main:app --port 8000 --reload`。
- 一次性安装：`python3 -m venv .venv && .venv/bin/python -m pip install -r requirements.txt`。
- 启动 uvicorn 和运行测试之前，先在同一个终端里导出数据库地址：`export DATABASE_URL="$(grep '^DATABASE_URL=' ../../.env.local | cut -d= -f2-)"`。
- 这一阶段 Next.js 不调用 Python 服务。不安装 Python，现有应用照样能运行。

### 路径
- 所有接口挂在 `/api` 下，例如 `/api/health`。以后接入前端时路径能和现有接口一一对应，对照测试也用同一套路径。

### 统一响应格式与错误映射
- 成功：路由调用 `success(data)`，返回 200 `{ requestId, ok: true, data }`。
- 失败：`{ requestId, ok: false, error }`，`error` 是字符串，额外信息放在 `data`，与 `lib/api/response.ts` 的 `error(message, data?)` 一致。

| 情况 | 状态码 | `error` |
| --- | --- | --- |
| 不存在的路由 | 404 | `"Not Found"` |
| 业务错误：主动抛 `HTTPException`，带明确状态码和可以公开的 `detail` | 原状态码 | `detail` 原样返回 |
| 需要附加数据的业务错误：抛 `ApiError(status, message, data)` | `status` | `message`；`data` 放进响应的 `data`，例如未登录时的 `{"code": "UNAUTHORIZED"}` |
| 字段校验失败 | **400** | 出错的字段和原因，例如 `"name: Input should be a valid string"`；**不带用户提交的值**。多个字段同时出错时怎么返回：只返回第一个错误 |
| 请求体不是合法 JSON，或整个没传 | **400** | `"invalid_request"`，与 `parseJsonBody`（`lib/api/route.ts`）一致：空请求体时 `req.json()` 同样抛 `SyntaxError` |
| 未捕获的异常 | 500 | `"internal_error"`，**不返回异常信息**；完整堆栈连同 requestId 写进日志 |

两类错误分开处理：

- **业务错误**是用户需要知道的，例如文件正在解析（KnowFlow 返回 409）、文件超过大小限制（413）。抛 `HTTPException`，状态码明确，`detail` 是可以展示给用户的文字。要在响应的 `data` 里附带信息时（`HTTPException` 的 `detail` 只是一个字符串，放不下），改抛自定义的 `ApiError`，由它的处理器调用 `failure(request, status, message, data)`；`failure` 只有收到 `data` 时才往响应里放 `data`，与 TS 版 `error(message, data?)` 一致。
- **意外错误**（代码 bug、数据库连不上）一律返回 500 `"internal_error"`。

落地要点：
- 异常处理器注册在 `starlette.exceptions.HTTPException` 上。它是 `fastapi.HTTPException` 的父类；只注册后者时，不存在的路由仍会返回 `{"detail":"Not Found"}`。
- 另外注册 `fastapi.exceptions.RequestValidationError` 和 `Exception` 的处理器。
- 校验错误的处理器只看第一条错误：`type` 是 `"json_invalid"`（不是合法 JSON），或 `loc` 只有 `("body",)`（请求体整个没传），返回 `"invalid_request"`；其余的去掉 `loc` 开头的 `"body"`，用 `.` 拼成字段名。缺请求体和缺字段的 `type` 都是 `"missing"`，只能靠 `loc` 区分。

### requestId
- 中间件在请求进来时生成（`uuid4`），存进 `request.state`；写进响应体的 `requestId` 和响应头 `X-Request-Id`；日志带上它。
- 500 的响应头由 500 的处理器（注册在 `Exception` 上）自己加上。原因：Starlette 把 `Exception` 的处理器放在最外层的 `ServerErrorMiddleware`，在中间件外面；未捕获的异常从中间件的 `call_next` 直接抛出，加响应头的那一步不会执行。4xx 的处理器在中间件里面（`ExceptionMiddleware`），响应照常经过中间件，不用另加。
- 前端传来合法 UUID 时优先使用它，否则自己生成；不是 UUID 的值一律不用。依据：KnowFlow 的聊天接口（`app/api/chat/stream/route.ts:83-85`）优先采用前端传来的 requestId，因为前端用同一个 UUID 作助手消息的 id（`lib/hooks/use-chat-stream.ts:411-412`）。前端把它放在聊天请求的 JSON 请求体里，不在请求头里，所以由聊天接口读取、校验后，覆盖中间件生成的值。这一阶段的接口前端都不传 requestId，只需要生成。

### 数据库连接
- 数据库地址从环境变量 `DATABASE_URL` 读取，不在代码里写死，也不在代码里解析 `.env.local`。
- `get_db()` 是一个带 `yield` 的依赖：每个请求用 `with psycopg.connect(...)` 建一条连接，交给路由使用，请求结束后自动关闭。暂时不用连接池。
- SQL 的参数一律用 `%s` 占位、单独传入，不拼字符串。
- `uuid` 类型的列查出来是 Python 的 `uuid.UUID`，在边界上统一转成字符串，和 TS 版一样，id 在代码里都是字符串。否则 `UUID(...) == "..."` 会悄悄返回 `False`，权限判断会出错。

### 当前用户
行为与 TS 版逐项对应：

| | Python | 对应的 TS 实现 |
| --- | --- | --- |
| cookie | 名字 `rag_session` | `lib/auth/cookie.ts` |
| 取当前用户 `get_current_user`（依赖） | 没有 cookie 时直接返回 `None`，不查数据库；否则关联 `sessions` 和 `users`，条件是 `sessions.id = token` 且 `expires_at > now()`，查到返回 `{id, email}`，查不到返回 `None` | `getCurrentUser`、`getSessionUser`（`lib/auth/current-user.ts`、`lib/auth/sessions.ts`） |
| 必须登录 `require_user`（依赖） | 没有当前用户时抛 `ApiError(401, "Unauthorized", {"code": "UNAUTHORIZED"})` | `requireUser` |
| `GET /api/auth/me` | 永远 200：`{user: {id, email}}` 或 `{user: null}`，供前端探测登录状态 | `app/api/auth/me/route.ts` |

业务路由在参数里声明 `user=Depends(require_user)`：没登录时路由函数根本不会执行，不再需要每个接口开头手写一遍检查。

### 测试数据
- 测试自己插入一个测试用户和一条会话，结束时删除用户（会话随外键 `ON DELETE CASCADE` 一起删掉），不依赖库里已有的数据。过期会话用 `expires_at = now() - interval` 构造。
- 测试会写数据库，所以 `DATABASE_URL` 的主机不是 `localhost` 或 `127.0.0.1` 时直接失败，避免误写远端数据库；没有导出 `DATABASE_URL` 时，数据库相关的测试跳过。

## 备选方案

### 放在单独的仓库
优点：
- 和产品代码完全隔离，不影响现有的 lint、构建和 CI

缺点：
- 两个版本要共用同一个 Postgres 和同一套手写迁移（`db/migrations/`，ADR-004），还要跑同一套对照测试；分仓后迁移和接口约定都要跨仓同步

### 测试客户端用 `httpx`
优点：
- 资料多，很多教程和旧版文档的示例都用它

缺点：
- 当前版本 Starlette（1.9.0）会优先导入 `httpx2`；只装 `httpx` 时每次运行测试都有弃用警告（2026-10-20 实测）

### 一条命令同时启动两个服务（npm `concurrently`、docker compose 或 Makefile 组合目标）
优点：
- 开发体验更好，只开一个终端

缺点：
- `concurrently` 是新的 npm 依赖；docker compose 要多维护一套容器配置
- 这一阶段 Next.js 不调用 Python 服务，没有“必须一起启动”的需要。接入前端时再定

### 保留 FastAPI 默认的 422 和 `{"detail": …}` 格式
优点：
- 不用写代码；客户端能拿到每个字段的完整错误

缺点：
- 和 KnowFlow 的 400 加统一格式不一致：违反“不改 API 响应格式”的约束，对照测试也过不了
- 默认的错误会把用户提交的值原样带回（`input`），登录接口会把密码返回给客户端

### 500 时像 KnowFlow 一样返回异常信息
优点：
- 调用方能直接看到出错原因

缺点：
- `lib/api/route.ts` 的 `routeErrorResponse` 会把 `e.message` 原样返回，数据库报错、表名等内部细节会泄露给客户端
- 用户需要看到的信息应该作为业务错误，用 4xx 和明确的 `detail` 返回，而不是靠 500 透传

### requestId 在构造响应时生成（照搬 `lib/telemetry/requestId.ts`）
优点：
- 和 TS 版完全一致，实现最简单

缺点：
- 处理请求期间拿不到 requestId，日志带不上。`lib/api/route.ts:20` 的 `console.error` 就没有 requestId：用户拿着响应里的 requestId 来报错时，找不到对应的日志

### 用 ORM（例如 SQLAlchemy）访问数据库
优点：
- 有类型化的模型和查询构造器，不用手写 SQL

缺点：
- 要在 Python 里再定义一遍表结构，而表结构的唯一来源是手写的 `db/migrations/`（ADR-004），两边容易不同步
- 现有查询少而简单，直接写 SQL 更容易和 TS 版逐句对照

### 用 asyncpg
优点：
- 性能好，原生异步

缺点：
- 只支持异步：所有用到数据库的依赖和路由都必须写成 `async def`。psycopg 同步、异步都支持，可以先用同步写法，FastAPI 会把同步路由放进线程池执行

### 用 python-dotenv 在代码里读取 `.env.local`
优点：
- 不用每次在终端里导出环境变量

缺点：
- 多一个依赖；代码和某个配置文件的路径绑在一起。用环境变量，代码不用关心配置从哪里来

### 401 也用 `HTTPException`
优点：
- 不用新增异常类

缺点：
- `detail` 只是一个字符串，放不下 `data.code`；KnowFlow 的 401 带着 `{"code": "UNAUTHORIZED"}`（`lib/auth/current-user.ts`）

### 测试复用库里已有的演示用户
优点：
- 不用在测试里插入数据

缺点：
- 依赖随时可能变化或被删除的数据（例如重新运行 `pnpm seed:demo`）；测试自己创建、自己删除，才能互不影响、反复运行

## 取舍

优点：
+ 和 KnowFlow 相同的响应格式和状态码，对照测试可以直接比较
+ 意外错误不会泄露内部信息；该让用户看到的错误走业务错误，照样能返回
+ 每条日志都能按 requestId 找到
+ 不影响现有的 Next.js 应用，不装 Python 也能运行
+ 鉴权行为和 TS 版逐项对应：同一个 cookie、同样的过期判断、401 带同样的 `code`、`/me` 同样永远返回 200

缺点：
- 开发时要多运行一个进程，Python 服务要做一次性安装
- 每个请求新建一条数据库连接，没有连接池；并发上来以后要换成连接池
- 数据库相关的测试要求本地 Postgres（Docker）在运行，并且导出了 `DATABASE_URL`
- 字段校验的错误文字来自 Pydantic，和 TS 版手写的文字不一样；前端会直接展示的错误信息，要在重写具体接口时逐个对齐
- 和 KnowFlow 有两处有意的行为差异：500 时的错误信息、requestId 的生成时机

## 影响

- 新接口一律挂在 `/api` 下，成功时返回 `success(data)`；需要让用户看到的错误抛 `HTTPException`，带明确的状态码和可以公开的 `detail`。
- 测试放在 `services/api/`，用 pytest 加 `TestClient` 运行。测试 500 时要用 `TestClient(app, raise_server_exceptions=False)`，否则异常会直接在测试里抛出。
- 要查数据库的代码用 `Depends(get_db)` 拿连接；要求登录的业务路由用 `Depends(require_user)`；需要附加数据的错误抛 `ApiError`。
- 什么时候引入连接池，等出现并发需求时再定。
- 重写聊天接口时：从请求体读取 `requestId`，校验是 UUID 后覆盖中间件生成的值，和 `app/api/chat/stream/route.ts:83-85` 的行为保持一致。
- 前端怎么接入 Python 服务（例如 Next.js 按路径前缀转发），另外写 ADR 决定。

## 备注

重写时发现 TS 版的两处问题：`routeErrorResponse` 在 500 时返回 `e.message`；它的错误日志没有带 requestId（`lib/api/route.ts:20-23`）。是否在 TS 版修复，另行决定。
